## 决策 4 · 同步/翻译分工（2026-08-25 确认）

**问题**：GitHub Action 定时跑 sync，但 Action 环境无本地 DeepSeek key，翻译是否需要/能否自动化？

**结论**：当前保持「自动同步 + 手动翻译」分工。

| 任务 | 工具 | 需要 API key？ | 运行方式 |
| ------ | ------ | -------------- | --------- |
| 同步上游（拉新代码 / version+1 / 重扫） | `sync.py` | ❌ 不需要（纯 git+文件+静态扫描） | ✅ GitHub Action 每天 03:00 UTC 自动跑 |
| 翻译描述（英→中） | `translate.py` | ✅ DeepSeek key | ⏰ 本地手动、低谷时段运行 |

**理由**：

1. `sync.py` 无任何 LLM/API 依赖，Action 环境（无 key）可正常运行——已实测通过。
2. `translate.py` 依赖 key + 受 DeepSeek 峰谷定价限制（工作日北京时间 09-12/14-18 全价，其余含周末 5 折）；Action cron 为 UTC 时间，自动翻译易撞高峰（贵）。
3. 权衡：自动同步保证内容不过时，手动翻译控制成本。

**未来改进（已计划，待项目稳定后）**：

- 在 GitHub Settings → Secrets 配置 `DEEPSEEK_API_KEY`。
- Action 中用 `${{ secrets.DEEPSEEK_API_KEY }}` 注入 translate 步骤。
- 处理 cron UTC → 北京时间高峰规避（或接受全价自动翻译）。
- 届时改为「全自动同步 + 全自动翻译」。

## 决策 3 · 全链路统一 YAML（2026-08-24 确认）

**问题**：skill-meta 用 JSON、index 用 YAML，两套格式是否统一？

**结论**：统一为 YAML（`skill-meta.yaml` + `index.yaml`），全链路只用 PyYAML。

**理由**：

1. 本项目 YAML 已无处不在——SKILL.md frontmatter、CLI 本地 skills.yaml、index.yaml；JSON 反而是异类。
2. 全链路一个解析器（PyYAML，`yaml.safe_load` 亦能解析 JSON），一套心智。
3. YAML 可注释、可读性好，适配「人工审核的精选索引」性质（§2.6 周维护有人工确认/改描述）。
4. 原规格与 CLI 已锁定 PyYAML，零新增依赖。

**反方（何时 JSON 更好）**：meta 交由强类型静态语言 / 前端 JS 消费且需严格无歧义解析时——backend 为 Python，不适用。

## 决策 2 · 分布式元数据 + 轻量索引（2026-08-24 确认）

**问题**：原设计用单一巨型 index.yaml 存所有 skill 元数据，skills 到 200+ 时会爆炸（文件巨大、整文件重写、并发冲突）。

**结论**：拆为两级——每 skill 一份 `skill-meta.yaml`（skill 级详情）+ 极简 `index.yaml`（仓库级装订页）。

| 文件 | 层级 | 角色 |
|------|------|------|
| `skill-meta.yaml` | skill 级 | 单 skill 详情（version/upstream_sha/risk/description_zh/source），与源码同目录 |
| `index.yaml` | 仓库级 | 每 skill 一行（id/name/version/risk/category），供 CLI 全局扫描 |

**理由**：skill-meta 管「单点精确读」（写侧主力），index 管「全局聚合扫描」（CLI 用 O(1) 请求扫全部版本）。单 skill 更新只改写 index 一行，天然错开并发冲突。`description_en` 不重复维护——从 SKILL.md frontmatter 读。

## 决策 1 · skills/ 目录按来源仓库分层（2026-08-24 确认）

**问题**：skills 会非常多且跨仓库大量重名（`code-review`/`handoff` 等通用名几乎每个合集都有），flat 存放必然撞车；合集仓库自带分类层级。

**结论**：`skills/<owner>/<repo>/[<category>/]<skill>/`，用来源仓库做顶层，后续层级原样保留上游结构（含分类 README）。

**理由**：

- 唯一标识天然 = `owner/repo/.../skill`，永不冲突。
- 保留来源可追溯；和 import/sync 逻辑天然一一对应。
- 分类层级直接复用上游结构，无需凭空发明编排。

**代价**（镜像 + 溯源模式下可接受）：路径变长；同一逻辑 skill 从多来源来会存多份，由索引层标注而非目录去重。

**连带影响**：import.py 必须能识别「合集仓库 ≠ 单 skill 仓库」，遍历仓库内所有 SKILL.md 逐个入库。
